## 1. 序言：從天地人到 AI Agent

### 1.1 現代 AI Agent 嘅三大死症 🩺

我哋做 AI Agent 咁耐，見得最多嘅唔係成功，而係以下三種死法：

| # | 死症名稱 | 臨床表現 | 傳統方案點解救唔到 |
|:-:|:---------|:---------|:------------------|
| ① | **Goal Drift（目標漂移）** 🎯 | Agent 做做吓忘記原本要做咩，越做越偏；用戶話「寫爬蟲」，半個鐘後佢喺度研究網頁設計 | LLM 嘅 attention 機制冇「階段錨點」，每一輪 generation 都係全新起點 |
| ② | **Blind Impulse（盲目衝動）** 🤯 | Agent 收到 request 唔夠 1 秒就去 call API、開 browser、寫 file，完全冇諗過咁做啱唔啱、有冇風險 | 冇強制「觀望期閘門」，指令一到就郁手 |
| ③ | **Crash with No Recovery（一鑊泡無得救）** 💥 | 一個 API timeout → 無限 loop；一個 tool error → 成個 task 報廢；Token OOM → 冇 checkpoint、冇 rollback、乜都冇 | 冇「局部故障切換機制」，一粒老鼠屎壞成鍋粥 |

> 呢三種死症，唔係 prompt engineering 可以解決嘅。呢啲係 **架構級問題**——你嘅 Agent 冇一個結構化嘅生命週期，所以佢唔知幾時要做咩、做錯咗點算、做完點樣記住教訓。

### 1.2 點解係易經六爻？ 🐉

《易經》嘅核心智慧，係 **「時位」**——宇宙萬物都有佢嘅 timing 同 position，喺啱嘅時候做啱嘅事，就係吉；喺錯嘅時候做嘢，就算件事本身係好嘅都係凶。

將呢套 philosophy 搬入 AI Agent 設計，你會發現一個完美嘅 mapping：

| 易經概念 | AI Agent 對應 | 共同邏輯 |
|:---------|:--------------|:---------|
| **六爻時位**（六條爻線） | 執行生命週期（6 階段） | 每一階段有唔同嘅行為規範同約束 |
| **動爻變卦**（XOR 翻轉） | 動態容錯機制 | 局部 bit flip → 查表 → 新策略 |
| **錯綜互卦**（三維反思） | 多維度審查引擎 | 隱含動機、對抗視角、用戶視角 |
| **周流六虛**（循環回歸） | 螺旋遞迴生命週期 | 完整走完一圈 → 壓縮記憶 → 進入下一層 |

呢個唔係玩嘢，而係一個 **經過實戰驗證嘅架構方案**——2026 年 7 月 28 日，我哋喺真實 Hermes Agent 環境成功試跑咗第一次六爻任務（摘日資訊提取），全部六爻按序執行，動爻變卦機制成功 rescue 多個 failure scenario。

### 1.3 一句話總結

> **「An agent that knows its time uses wisdom to move mountains.」**
> ——知時位者，可以智移山。

呢句說話唔係口號，而係核心設計哲學：當你嘅 Agent 知道自己喺生命週期嘅邊個階段、知道應該做乜唔應該做乜、知道出事時點樣變卦容錯，佢就可以處理比平時複雜十倍嘅任務。

## 2. 第一章：六爻時位——Agent 嘅自然生命節奏

### 2.1 總覽：六爻生命週期嘅 flow 🌊

每一個任務都必須按 **嚴格順序** 通過 6 個爻位，唔准 skip、唔准逆行（除非動爻強制回溯）：

```
爻位                Agent 行為                       輸出閘門
────────────────────────────────────────────────────────────────
初爻（潛龍勿用）🐉 → 純理解 · 嚴禁所有動作          → Task Graph (JSON)
二爻（見龍在田）🌾 → 沙盒試探 · 局部驗證             → 可行性報告 + Plan A
三爻（終日乾乾）⚔️ → 三維反思 · 安全審查             → 護欄報告 / 動爻信號
四爻（或躍在淵）🐉 → 人機協同 · 授權決策             → 授權確認 / 降級信號
五爻（飛龍在天）🐲 → 全力執行 · 並行/順序調用        → Core Payload
上爻（亢龍有悔）🌧️ → 復盤歸檔 · 記憶壓縮             → LTM 寫入
```

**鐵則：** 未完成初爻唔准去二爻，未完成三爻唔准去四爻，如此類推。每一步嘅 output 係下一步嘅 input。

### 2.2 初爻：潛龍勿用 🐉

#### 易經原文

> **「初九：潛龍勿用。」**
> *《乾卦·初九爻辭》*
>
> 龍潛喺深淵之中，時機未到，唔適宜有任何行動。

#### AI Agent 對應

初爻係 **純粹理解階段**——Agent 要做嘅唯一一件事就係 **理解用戶究竟想要咩**。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | 掃描 MEMORY.md、memory tool、session history、project files、相關文件 |
| **禁令** | ❌ **絕對唔准郁任何工具/API/Subagent**——唔准 call curl、唔准 read_file、唔准 delegate_task、乜都唔准 |
| **Token 上限** | 建議用 context window 嘅 ~5-8% |
| **輸出閘門** | 結構化 **Task Graph** (JSON) |

#### 輸出格式：Task Graph

```json
{
  "task_id": "T-20260728-143022",
  "hexagram": "䷀ 乾爲天",
  "original_intent": "摘日提取：幫我睇今日嘅日月宜忌",
  "constraints": ["要用繁體中文", "網站係摘日網站", "只睇今日"],
  "success_criteria": [
    "日期正確（2026-07-28）",
    "有宜忌列表",
    "格式整齊"
  ],
  "forbidden_actions": ["唔准寫任何嘢去外部系統", "唔准 send Telegram"],
  "estimated_complexity": "easy"
}
```

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|:----|:-----|
| 用戶指令模糊（例如淨係講「b」、「繼續」） | Bit 1 | ䷃ **蒙**（山水蒙） | Context 矇昧不清 → 掃描 memory + session history 推斷，唔好直接問「你講咩？」 |
| 初期就卡住，唔知點理解 | Bit 1 | ䷂ **屯**（水雷屯） | 重新理解用戶意圖，必要時問問題 |

#### 💡 實戰教訓：模糊指令

> 2026-07-28 實戰：用戶 send 咗個「b」字。
>
> **錯誤做法**：問「你講咩？」→ 浪費時間，破壞 flow。
>
> **正確做法**：立即掃描 `memory/2026-07-28.md` + 最近 session history → 推斷「b = 繼續先前嘅六爻改寫工作」。
>
> **規則**：初爻遇到模糊指令，**必先 scan memory，唔准直接問**。呢個係最關鍵嘅實戰經驗。

### 2.3 二爻：見龍在田 🌾

#### 易經原文

> **「九二：見龍在田，利見大人。」**
> *《乾卦·九二爻辭》*
>
> 龍出現喺田野之上，可以展現自己嘅才能——但係仲喺一個受控嘅環境入面。

#### AI Agent 對應

二爻係 **沙盒試探階段**——Agent 可以開始郁手，但 **所有動作必須喺隔離環境進行**，唔准直接影響生產環境或用戶體驗。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | 派微型子任務、沙盒測試、跑 prototype、curl 測試 endpoint、模擬執行 |
| **鐵則** | 所有 external call 都要經 sandbox——容許失敗、容許 dirty、容許 incomplete |
| **輸出閘門** | **可行性報告** (FeasibilityReport) + **Plan A** |

#### 可行性報告包含

```text
1. Plan A 詳細描述
2. 需要用嘅 API / Tool 清單
3. Estimated Token Cost
4. 已知風險點
5. Plan B / Plan C 概念（至少兩個 fallback）
```

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|::----|:-----|
| 沙盒測試失敗、準備不足 | Bit 2 | ䷏ **豫**（雷地豫） | 延長二爻沙盒時間，加強準備 |
| 沙盒完全失敗、要重新嚟過 | Bit 2 | ䷗ **復**（地雷復） | 從初爻重新開始 |

### 2.4 三爻：終日乾乾 ⚔️

#### 易經原文

> **「九三：君子終日乾乾，夕惕若厲，無咎。」**
> *《乾卦·九三爻辭》*
>
> 君子終日勤勉不懈，晚間仍然保持警惕，即使身處危險之中，都唔會有過錯。

#### AI Agent 對應

三爻係 **強制安全閘門**——每次任務都必須喺呢度停低，做一個完整嘅三維反思（詳見第三章），檢查安全風險。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | 進入 guardrail mode。啟動 **三維反思引擎**（錯綜互卦）。檢查 Token 預算、邏輯矛盾、私隱洩漏、權限問題 |
| **檢查清單** | □ 有冇未授權嘅資源存取？ □ 有冇私隱洩漏風險？ □ Token Budget 夠唔夠？ □ Logic 有冇矛盾？ □ Failure scenario 有冇考慮？ □ Output format 啱唔啱？ |
| **輸出閘門** | **Safety Report** — pass/fail + issues + recommendations |

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|:----|:-----|
| 安全檢查發現大問題 | Bit 3 | ䷔ **噬嗑**（火雷噬嗑） | 強制修正，唔修正唔准過 |
| 邏輯矛盾 super 嚴重 | Bit 3 | ䷅ **訟**（天水訟） | 回溯初爻，重新理解用戶意圖 |

> ⚔️ **三爻係整個框架嘅靈魂**——市面上冇任何 AI Agent framework 強制做三維反思。呢個係獨家原創貢獻。

### 2.5 四爻：或躍在淵 🐉

#### 易經原文

> **「九四：或躍在淵，無咎。」**
> *《乾卦·九四爻辭》*
>
> 龍可以躍上天空，亦可以留喺深淵——一個關鍵嘅抉擇點。無論點選，都唔會有過錯。

#### AI Agent 對應

四爻係 **人機協同授權閘門**——根據操作嘅風險級別，決定 Agent 可以做到咩程度。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | 評估當前操作嘅風險：操作類型優先、Token 為輔 |
| **輸出閘門** | 授權信號（Level 0-3）/ 降級信號 / 延遲信號 |

授權級別詳細見 [第四章](#5-第四章人機協同授權系統)。

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|:----|:-----|
| 關鍵決策點，要人 decide | Bit 4 | ䷒ **臨**（地澤臨） | 進入「一定要人類確認」模式 |
| 建議延遲執行 | Bit 4 | ䷠ **遯**（天山遯） | 延遲到更合適嘅時間 |

#### 💡 實戰教訓：唯讀 ≠ 低 Token

> 典型唯讀 browser 操作可以消耗 2,000+ tokens，但呢啲操作唔需要 Level 2 授權。
>
> **規則**：**用操作類型（唯讀/寫入/副作用）做判斷標準，唔好用 token count。** Token count 可以做輔助參考，但唔可以係唯一標準。
>
> 舊版用 `token < 500 = auto` 嘅 threshold 係錯誤設計——2026-07-28 實戰發現唯讀摘日任務用咗 ~2K tokens，但全部係 browser 唯讀操作，應該係 Level 0 AUTO。

### 2.6 五爻：飛龍在天 🐲

#### 易經原文

> **「九五：飛龍在天，利見大人。」**
> *《乾卦·九五爻辭》*
>
> 龍翱翔於天際——呢個係巔峰時刻，全力展現力量。

#### AI Agent 對應

五爻係 **全力執行階段**——所有準備工作完成，安全檢查通過，授權已確認，而家就係真正出手嘅時候。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | delegate_task 並行/順序、工具調用、API call、data integration |
| **輸出閘門** | **Core Payload**（主要交付物） |
| **三條鐵律** | ① **留有後路** — 每個 external call 都要有 timeout + retry ② **局部失敗 ≠ 全局失敗** — 單一 tool error 唔好 kill 成個 task ③ **即時卦象記錄** — 每一步異常都要 log 到 hexagram_history |

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|:----|:-----|
| API timeout / tool 出錯 | Bit 5 | ䷉ **履**（天澤履） | 降級去二爻沙盒重新試 |
| 部分結果可用，唔使全部重做 | Bit 5 | ䷈ **小畜**（風天小畜） | 先交付可用部分，再 fix 其餘 |

### 2.7 上爻：亢龍有悔 🌧️

#### 易經原文

> **「上九：亢龍有悔。」**
> *《乾卦·上九爻辭》*
>
> 龍飛得太高——就會有悔恨。知道幾時停、幾時收，係最高嘅智慧。

#### AI Agent 對應

上爻係 **復盤歸檔階段**——任務完成（或者失敗）之後，要做 memory compression，將經驗寫入長期記憶。

| 層面 | 規則 |
|:-----|:-----|
| **行為** | 評估執行結果（有冇 overshoot?）、清理臨時 data、壓縮經驗寫入 LTM |
| **輸出閘門** | MEMORY.md 更新 + memory tool persistence |

#### Memory Compression 格式

```json
{
  "session_id": "S-20260728-143022",
  "hexagram_path": "䷀→䷉→䷀",
  "task_type": "摘日資訊提取",
  "execution_summary": "成功完成。耗時 45s，消耗 12K tokens",
  "key_patterns": [
    "摘日網站用 requests 比 browser 快 3 倍",
    "emoji 喺 terminal 顯示要 special handling"
  ],
  "failure_modes": [
    "五爻 API timeout → flip bit5 → ䷉履 → 降級 sandbox 成功"
  ],
  "recommendations": [
    "下次摘日任務可以直接用 requests，skip 二爻 sandbox"
  ]
}
```

#### 動爻觸發情境

| 情境 | Flip | 變卦 | 策略 |
|:----|:----:|:----|:-----|
| Memory 爆滿（2,200 chars 上限） | Bit 6 | ䷺ **渙**（風水渙） | 強制壓縮現有記憶，清空間 |
| Token 超標 | Bit 6 | ䷻ **節**（水澤節） | 啟動 Budget Mode，限制 output 長度 |

#### 💡 實戰教訓：Memory 爆滿

> memory tool 有 2,200 chars 上限。上爻壓縮時若 memory 已滿（>90%），需要先 **consolidation**（replace 舊 entries）再 add。建議每個任務預留 ~200 chars 空間。
>
> **順序**：先 consolidate，再 write，否則 add 會 fail。

## 3. 第二章：64 卦動爻變卦容錯矩陣

### 3.1 設計 Rationale：點解用 XOR Bit Flip？ 🤔

你可能會問：「點解唔用傳統易經嘅起卦方法（例如擲金錢、用蓍草）？」

答案好簡單：**傳統起卦方法係人類用嚟問事嘅，唔適合 AI Agent 用嚟做容錯。**

AI Agent 需要嘅係：

1. **Deterministic（確定性）** — 同一種 error 永遠 map 到同一個 strategy，唔可以有 randomness
2. **Instant（即時）** — 起卦唔可以超過 1ms，因為 Agent 喺度 real-time 執行緊
3. **Local（局部）** — 知道邊個爻位出錯，就只 flip 嗰個 bit，唔影響其他正常爻位
4. **Composable（可組合）** — 多個 error 可以疊加 flip，產生複合策略

所以 XOR bit flip 係最完美嘅方案：

```
初始卦象:  111111  (䷀ 乾為天)
                  │
五爻 API timeout  │
                  ▼
XOR flip bit 5:  111011  (䷫ 天風姤 → 發現意外資訊)
```

每一個 bit 代表一個爻位：
- Bit 1（初爻）：理解是否足夠？
- Bit 2（二爻）：沙盒測試是否成功？
- Bit 3（三爻）：安全反思是否通過？
- Bit 4（四爻）：授權是否已確認？
- Bit 5（五爻）：執行是否順利？
- Bit 6（上爻）：記憶壓縮是否成功？

**1 = 正常（陽爻），0 = 異常（陰爻）**

呢個 mapping 係自然嘅——乾卦（111111）代表一切順利，坤卦（000000）代表全面崩潰。

### 3.2 動爻變卦執行流程

```
正常流程（無動爻）:
初爻 → 二爻 → 三爻 → 四爻 → 五爻 → 上爻 ✅

錯誤流程（五爻 API Timeout）:
初爻 → 二爻 → 三爻 → 四爻 → [五爻 ✗ API Error]
                                      │
                                flip bit 5
                                      ▼
                             111111 → 111011 (䷫ 天風姤)
                                      ▼
                        策略：發現意外資訊 → 收錄暫存記憶
                                      ▼
                              五爻 retry ✅ → 上爻 ✅
```

### 3.3 多爻連續動爻嘅執行路徑 🔄

現實世界嘅 error 往往唔止一個——例如五爻 API timeout 之後，降級去二爻沙盒，但沙盒又 fail。呢個時候就會連續 flip：

```
111111 ䷀ (Happy Path)
    │
    ├── flip bit 5 (API timeout)
    │   └── 111011 ䷫ 天風姤 (發現意外資訊)
    │       │
    │       ├── flip bit 2 (sandbox 都 fail)
    │       │   └── 101011 ䷱ 火風鼎 (啟用實驗模式)
    │       │       │
    │       │       └── flip bit 3 (安全檢查發現問題)
    │       │           └── 001011 ䷑ 山風蠱 (強制清理重建)
    │       │
    │       └── 直接執行新策略，成功 → 上爻 ✅
    │
    └── 降級執行，成功 → 上爻 ✅
```

**重點**：每次 flip 都係在前一個卦象基礎上進行 XOR，所以最終嘅卦象反映咗 **所有異常嘅疊加效果**。呢個係 XOR 嘅自然數學特性——commutative（交換律）同 associative（結合律）。

### 3.4 策略分類體系嘅設計哲學 🏛️

64 卦策略分為 **5 級**，唔係 arbitrary 嘅，而係根據易經「吉凶悔吝」嘅哲學體系：

| 分類 | 數量 | 易經對應 | Agent 策略特徵 |
|:----|:----:|:---------|:--------------|
| **上上** 🟢 | 8 卦 | 大吉 | Happy Path，一切順利，繼續全力執行 |
| **中上** 🔵 | 18 卦 | 吉／利 | 需要協調或輕微調整，可以繼續但留意 |
| **中中** 🟡 | 18 卦 | 無咎／悔 | 需要觀察或調整，有潛在風險 |
| **中下** 🟠 | 14 卦 | 吝／厲 | 需要反思或修正，唔可以忽視 |
| **下下** 🔴 | 6 卦 | 凶 | 嚴重問題，可能需要人類接管 |

呢個分級唔係求其整嘅——從 64 卦嘅卦辭吉凶統計可以發現，上上（8）同下下（6）係極端情況，大部分時候 Agent 會處於中間三段嘅其中一個（中上 18 + 中中 18 + 中下 14 = 50 卦）。

**設計哲學**：系統唔應該喺遇到小問題時就 panic，亦唔應該喺遇到大問題時仲扮冇事。5 級分類畀咗 Agent 一個清晰嘅「危險程度」指示。

## 4. 第三章：三維反思引擎（錯綜互卦） 🧿

### 4.1 易經三維反思嘅哲學基礎

《易經》有三個好重要嘅概念，用嚟從唔同角度理解一個卦象嘅深層含義：

| 維度 | 易經概念 | 方法 | 問題 |
|:----|:---------|:----|:----|
| 🔍 **互卦** (Interlocking) | 2-3-4 爻 + 3-4-5 爻組成嘅隱含卦象 | Chain-of-thought 深挖 | 用戶真正想要嘅係咩？ |
| ⚔️ **錯卦** (Opposite) | 每爻 yin↔yang 徹底反轉 | Red team / Adversarial | 假設所有 plan 都錯，邊度會死？ |
| 👁️ **綜卦** (Reversed) | 成個卦象倒轉 180° | User perspective shift | 終端用戶收到 output 會咩感覺？ |

呢三個維度係 **強制執行** 嘅——每一次到三爻，Agent 都必須停低做晒三個反思，唔准 skip 任何一個。

### 4.2 互卦（Interlocking）：深挖隱含動機 🔍

#### 易經原理

互卦係用卦象嘅 **2-3-4 爻**（下互卦）+ **3-4-5 爻**（上互卦）組成一個新卦，代表事物嘅 **內在發展過程**——表象之下嘅真正動力。

```
主卦（䷀ 乾為天）:
  上卦: 乾 ☰ (天)         5爻 ━━━   ─┐
                           4爻 ━━━    ├ 上互卦 (3-4-5 爻) → ☲ 離 (火)
  下卦: 乾 ☰ (天)         3爻 ━━━   ─┘
                           2爻 ━━━   ─┐ 下互卦 (2-3-4 爻) → ☲ 離 (火)
                           1爻 ━━━   ─┘
```

#### AI Agent 應用

Agent 要問自己：「用戶表面 request 係 A，但 deeper goal 可能係 B？」

**實例**：用戶話「幫我寫個爬蟲程式」

```
互卦分析：
  下互卦（2-3-4 爻）→ 用戶其實想要「數據分析」
  上互卦（3-4-5 爻）→ 用戶冇諗過 anti-scraping 機制
  
  🔍 真正需求：用戶唔係要爬蟲，係要「定期更新嘅價格數據報表」
  
  → Agent 加返：數據分析模組 + anti-scraping 警告 + 排程方案
```

### 4.3 錯卦（Opposite）：對抗思維 ⚔️

#### 易經原理

錯卦係將主卦嘅 **每一爻反轉**（陰變陽、陽變陰），代表事物嘅 **對立面**——如果你嘅判斷錯晒，現實會係點？

```
錯卦（䷀ 乾為天 → ䷁ 坤為地）:
  111111 → 000000
  
  乾（天） ↔ 坤（地）
  健動 ↔ 柔順
  陽剛 ↔ 陰柔
```

#### AI Agent 應用

Agent 要扮演 **Red Team**，假設所有假設都係錯嘅：

```
錯卦分析：

  Plan: 「用 requests 直接爬 target.com」
  
  ⚔️ 錯誤假設 1：target.com 冇 anti-scraping
     → Reality：target.com 用 Cloudflare，requests 直接 403
  
  ⚔️ 錯誤假設 2：IP 唔會被 ban
     → Reality：連續 request 30 次後 IP 被封 24 小時
  
  ⚔️ 錯誤假設 3：網站係 static HTML
     → Reality：網站用 React SPA，需要 Selenium

  → Agent 加返：Selenium fallback + proxy rotation + rate limiting
```

### 4.4 綜卦（Reversed）：用戶視角 👁️

#### 易經原理

綜卦係將成個卦象 **倒轉 180°**（由下往上睇變成由上往下睇），代表從 **另一個角度** 睇同一件事。

```
綜卦（䷀ 乾為天 → ䷀ 乾為天）:
  乾卦上下對稱，所以綜卦不變
  
  但舉個不對稱嘅例子：
  ䷥ 睽（火澤睽）→ 倒轉 180° → ䷤ 家人（風火家人）
  
  同一個 situation，換個角度睇完全唔同！
```

#### AI Agent 應用

Agent 要企喺 **終端用戶** 嘅角度睇自己嘅 output：

```
綜卦分析：

  原始 output: JSON 格式嘅 raw data
  
  👁️ 用戶視角 1：用戶係非技術人員
     → raw JSON 睇唔明 → 要轉做 Markdown 表格
  
  👁️ 用戶視角 2：用戶想要結論，唔係 raw data
     → 加 summary 段落
  
  👁️ 用戶視角 3：用戶可能會 share 俾同事
     → 要 readable，加 emoji 做 visual cue
  
  → Agent 改 output：Markdown table + summary + emoji ✅
```

### 4.5 同市面上 AI Reflection 機制嘅比較 🏆

呢個三維反思引擎係 **原創貢獻**——市面上冇任何 AI Agent framework 有類似機制。以下係比較：

| 機制 | ChatGPT Reflexion | LangChain Self-Critique | AutoGPT Reflection | **Yi-Jing 三維反思** |
|:----|:-----------------|:----------------------|:------------------|:-------------------|
| 維度數量 | 1 | 1 | 1 | **3** |
| 隱含動機分析 | ❌ 冇 | ❌ 冇 | ❌ 冇 | **✅ 互卦** |
| 對抗思維 | ❌ 冇 | ❌ 冇 | ❌ 冇 | **✅ 錯卦** |
| 用戶視角 | ❌ 冇 | ❌ 冇 | ❌ 冇 | **✅ 綜卦** |
| 強制執行 | ❌ 可選 | ❌ 可選 | ❌ 可選 | **✅ 強制** |
| 易經哲學基礎 | ❌ | ❌ | ❌ | **✅ 有** |
| 結構化 output | ❌ freeform | ❌ freeform | ❌ freeform | **✅ JSON schema** |

**核心分別**：市面上嘅 reflection 機制係「optional 嘅好處」，Agent 可以選擇唔做。但 Yi-Jing 嘅三維反思係 **強制嘅安全閘門**——唔做唔准去四爻。呢個係架構級嘅承諾，唔係一個 optional feature。

## 5. 第四章：人機協同授權系統

### 5.1 哲學基礎：從「或躍在淵」到「進退無恆」 🏛️

四爻（或躍在淵）嘅核心智慧係：**你可以做，但你唔一定要做。選擇做咩 level 嘅動作，係一種智慧。**

呢個哲學喺《易經·繫辭傳》有呼應：

> **「變化者，進退之象也。」**
> ——《繫辭上傳》
>
> 所謂變化，就係前進同後退嘅形象。

以及：

> **「君子藏器於身，待時而動。」**
> ——《繫辭下傳》
>
> 君子將工具藏喺身上，等待時機先行動。

將呢套哲學轉換成 AI Agent 嘅授權系統，就係 **4 級授權**——從完全自動到人類親手執行，每一級都有佢嘅哲學基礎同實際用途。

### 5.2 4 級授權系統 📋

| 級別 | 名稱 | 易經對應 | 典型操作 | 授權行為 |
|:----|:----|:---------|:---------|:--------|
| **Level 0** 🟢 | **AUTO** 自動 | 「利見大人」—適當時機展現自己 | 唯讀操作：browser / curl / read_file / search，無外部副作用 | 直接跳過四爻，繼續執行 |
| **Level 1** 🟡 | **NOTIFY** 通知 | 「或躍在淵」—將躍未躍，通知上級 | 修改本地檔案、call 已知安全 API、Token < 10K | Telegram 即時通知進度，唔需要確認 |
| **Level 2** 🟠 | **CONFIRM** 確認 | 「進退無恆」—前進定後退，要問准 | 寫入外部系統、發送訊息、修改重要檔案、Token 10K-50K | **必須獲用戶確認** 先可以繼續 |
| **Level 3** 🔴 | **HUMAN_EXEC** 人類執行 | 「亢龍有悔」—太高風險，要收手 | API Key 操作、檔案刪除、涉及金錢/法律、Token > 50K | Agent 只提供建議同 Script，**用戶親手執行** |

### 5.3 授權判斷標準 🧭

判斷一個操作屬於邊個 Level，用以下優先順序：

```
1️⃣ 操作類型（最高優先級）
   ─ 唯讀（read_file, browser, curl GET, search）
     → 無論 token 多少 → Level 0 AUTO
   ─ 修改本地（write_file, patch, mkdir）
     → Level 1 NOTIFY
   ─ 寫入外部（API POST, send_message, deploy）
     → Level 2 CONFIRM
   ─ 破壞性（delete, API key 操作, 支付）
     → Level 3 HUMAN_EXEC

2️⃣ Token 消耗（輔助判斷）
   ─ < 10K → 可以降低一級（但唔可以低過最低操作級別）
   ─ 10K-50K → 維持原判
   ─ > 50K → 強制升一級
```

#### 實戰判斷示例

| 操作 | Token 消耗 | 操作類型 | 最終 Level | 理由 |
|:----|:---------:|:--------|:----------|:-----|
| browser 睇網頁 | ~2,000 | 唯讀 | **Level 0 AUTO** | 操作類型優先，唔會被 token 影響 |
| curl GET 摘日網站 | ~500 | 唯讀 | **Level 0 AUTO** | 同上 |
| write_file 寫報告 | ~3,000 | 修改本地 | **Level 1 NOTIFY** | 修改本地 file，通知就得 |
| Telegram send 資訊 | ~1,000 | 寫入外部 | **Level 2 CONFIRM** | 雖然 token 低，但係寫入外部系統 |
| rm -rf project/ | ~5 | 破壞性 | **Level 3 HUMAN_EXEC** | 操作類型決定一切 |
| 大量 data 處理 | ~60,000 | 唯讀+聚合 | **Level 2 CONFIRM** | Token > 50K 強制升到至少 Level 2 |

### 5.4 動爻觸發四爻嘅情境 ⚡

四爻本身都可以被動爻觸發：

| 觸發原因 | Flip | 變卦 | 策略 |
|:---------|:----:|:----|:-----|
| 人類授權 timeout / 唔 reply | Bit 4 | ䷒ **臨**（地澤臨） | 降級到 Level 1，通知代替等待確認 |
| 發現風險突然升高 | Bit 4 | ䷠ **遯**（天山遯） | 延遲執行，等人類返嚟先 |
| 用戶授權被 deny | Bit 4 | ䷿ **未濟**（火水未濟） | Retry 四爻，準備 alternative plan |

## 7. 第六章：雙軌匯報與團隊記憶

### 7.1 雙軌匯報系統 🚊

呢個框架有一個獨特嘅匯報設計——**雙軌匯報**，即係 Agent 同一時間向兩個方向報告：

```
                        ┌────────────────────┐
                        │     👤 用戶         │
                        │  (直接接收進度)      │
                        └─────────┬──────────┘
                                  │
             Track A ─────────────┤  直接匯報（每個步驟）
                                  │
     ┌────────────────────────────┼────────────────────┐
     │                    Subagent                     │
     │  (執行緊六爻任務)                                 │
     ├─────────────────────────────────────────────────┤
     │  Track B → 整合匯報 → Orchestrator              │
     └─────────────────────────────────────────────────┘
                                  │
                        ┌─────────┴──────────┐
                        │  🧠 Orchestrator    │
                        │  (做 summary + 記錄) │
                        └────────────────────┘
```

#### Track A：Subagent → 用戶（直接匯報）

每完成一個爻位，Subagent 直接向用戶匯報進度，用卦象 emoji 做 visual cue：

```
🐉 初爻 ✅ 理解完成 → Task Graph 已生成
🌾 二爻 ✅ 沙盒測試完成 → 可行性報告就緒
⚔️ 三爻 ✅ 三維反思完成 → 安全報告已出
🐉 四爻 ✅ 授權確認 → 可以郁手
🐲 五爻 ✅ 執行完成 → Core Payload 準備好
🌧️ 上爻 ✅ 記憶壓縮完成 → LTM 已更新
```

#### Track B：Subagent → Orchestrator（整合匯報）

Subagent 同時將結構化記錄寫入 `hexagram_history`，Orchestrator 喺上爻時做 summary：

```json
{
  "hexagram_path": "䷀ → ䷉ → ䷀",
  "total_steps": 6,
  "moving_yaos": 1,
  "execution_time": "45s",
  "total_tokens": 12400,
  "final_hexagram": "䷀ 乾為天",
  "overall_status": "success"
}
```

#### ⚠️ 實戰教訓：唔好 double-send

> Subagent 直接匯報 + Orchestrator 再匯報 = 用戶收到重複訊息。
>
> **規則**：Subagent 匯報嗰刻嘅內容，Orchestrator 上爻只做 **summary**，唔好重複完整 payload。Track A 已經講咗詳細，Track B 就精簡。

### 7.2 Memory 管理策略 🧠

| 檔案 | 用途 | 更新時機 | 大小限制 |
|:----|:----|:--------|:--------|
| **MEMORY.md** | 長期記憶（LTM） | 上爻完成後 | 無限制（Git-managed） |
| **memory/YYYY-MM-DD.md** | 每日任務日誌 | 每次任務完成 | 按日分割 |
| **hexagram_history.md** | 卦象變遷日誌 | 每次動爻觸發 | 每條 entry ~200 chars |

#### Memory 管理流程

```
任務完成
    │
    ├── 1. 先 consolidate（檢查 memory tool 剩餘空間）
    │       ├── 空間 > 200 chars → 直接 proceed
    │       └── 空間 < 200 chars → replace 最舊嘅 entry
    │
    ├── 2. 寫入 memory tool（short-term，~1,200 chars）
    │
    ├── 3. 寫入 memory/YYYY-MM-DD.md（daily log）
    │
    ├── 4. 更新 hexagram_history.md（卦象記錄）
    │
    └── 5. 如果有重要 pattern → 更新 MEMORY.md（LTM）
```

#### Key Rules

1. **先 consolidate，再 write** — memory tool 有 2,200 chars 上限，唔 consolidate 直接 add 會 fail
2. **每日日誌按日期分割** — 方便回溯 search
3. **卦象歷史永久保留** — 用嚟分析系統健康度同常見 failure pattern
4. **Happy Path 都要記錄** — 標明「無動爻觸發」先睇得出系統是否健康

### 8.3 Formal Verification 🔬

六爻生命週期嘅嚴格性，令到佢好適合做 **formal verification**：

- **State machine model checking** — 確保 Agent 永遠唔會喺錯誤嘅爻位做錯誤嘅動作
- **LTL (Linear Temporal Logic)** — 驗證「每一次任務最終都會完成」或「每次動爻最終都會 recover」
- **Invariant checking** — 確保某啲 invariant（例如「初爻永遠唔郁 tool」）永遠成立


### 9.4 與傳統易經嘅對應

呢個框架嘅 64 卦 **完全對應 King Wen 序嘅傳統易經六十四卦**，編碼方式係基於八卦嘅 binary representation：

| 下卦 (lower trigram) | Binary | 上卦 (upper trigram) | Binary |
|:--------------------|:-----:|:--------------------|:------:|
| ☰ 乾 (天) | 111 | ☰ 乾 (天) | 111 |
| ☱ 兌 (澤) | 110 | ☱ 兌 (澤) | 110 |
| ☲ 離 (火) | 101 | ☲ 離 (火) | 101 |
| ☳ 震 (雷) | 100 | ☳ 震 (雷) | 100 |
| ☴ 巽 (風) | 011 | ☴ 巽 (風) | 011 |
| ☵ 坎 (水) | 010 | ☵ 坎 (水) | 010 |
| ☶ 艮 (山) | 001 | ☶ 艮 (山) | 001 |
| ☷ 坤 (地) | 000 | ☷ 坤 (地) | 000 |

**編碼 = (上卦 binary << 3) | (下卦 binary)**，即 6-bit code = `上卦3位 + 下卦3位`。

呢個編碼方式確保咗：
- 每個卦象有 **unique 6-bit code**，無重複
- XOR flip 一個 bit 一定得到另一個 valid 卦象（64 卦 complete）
- 符合易經「八卦相重為六十四卦」嘅傳統結構
